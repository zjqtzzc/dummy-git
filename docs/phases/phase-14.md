## 要解决什么问题

现在每个列表一次只能选中一样东西，所以每个操作也只作用于一样东西。碰到「同一件事要对好几样东西做」，就只能一样一样来：

- **把一个修复摘到发布分支**：修复是三条提交。现在要右键 Cherry-Pick 三次，顺序得自己记着从旧到新；第二条冲突了，解决完还得记得第三条还没摘。
- **撤掉一串提交**：Revert 同理，而且顺序要反过来，从新到旧。
- **把几条提交的 hash 贴给别人**：一条一条复制。

需求池里还有两件事等着多选：批量删除、更新分支，以及 Rollback 改成「作用于选中的文件」。Squash、批量 Drop 也要先有多选。

这件事拆成两个阶段（第 1 条）。**本阶段只做提交列表**；分支树和 Commit 面板的多选是第 15 阶段（`phases/phase-15.md`），用的是本阶段做出来的同一套选中规则和右键菜单做法。

## 难在哪

「选中」从一个变成一组，下面四件事随之出现，后面每一节回答其中一件：

1. **怎么选、选了以后什么跟着变**（第一节）。键盘、鼠标怎么加选、减选；选了一组时，diff 和右栏显示什么；刷新以后选中还留不留。
2. **右键菜单拿不到整组**（第二节、第四节 B）。右键菜单是 VS Code 原生的，它只读**被右键的那一行**身上写的信息，不知道别的行也被选中了。办法已经实测可行（2026-10-19）。
3. **一组操作会停在一半**（第三节）。单条 cherry-pick 要么成功、要么停一次；一串里第二条冲突了，第一条已经摘过来，第三条还没动。这时继续做的是什么、放弃会撤掉什么，都要定。还有两种只在一串里才碰到的情况：某条的改动当前分支已经有了（「变空」），以及中间夹着合并提交。
4. **有些操作对一组没有意义**（第二节）。Reset 到哪里、改哪条的说明，都只能对一条做；多选时这些菜单项要去掉。

## 一、怎么选，选了以后什么跟着变

1. **拆成两个阶段**（2026-10-19 项目负责人定）：要做的一共十步左右，超过一个阶段 8 步的上限。先在提交列表上把选中规则和右键菜单跑通，第 15 阶段的树直接接上。不拆的代价：一个阶段跨三块面板，中间没法分段验收。
2. **键位**（2026-10-19 项目负责人定）：

   | 操作 | 结果 |
   |---|---|
   | 单击、↑↓ | 只选这一行（和现在一样） |
   | Ctrl+单击 | 这一行加进选中，或者从选中里去掉，其余不动 |
   | Shift+单击 | 从「锚点」到这一行整段选中，替换掉原来的 |
   | Ctrl+Shift+单击 | 这一段**加进**原来的选中 |
   | Shift+↑↓ | 锚点不动，选中范围的另一头上下挪一行 |
   | Ctrl+A | 全选 |

   Mac 上 Ctrl 换成 Cmd。锚点是最近一次单击或 Ctrl+单击的那一行。和 VS Code 原生列表、IDEA 一样。
   - 否决 VS Code 的 Ctrl+↑↓（只挪光标不选）加 Ctrl+空格（切换选中）：会多出「光标所在的行没被选中」这种状态，而键盘多选用 Shift+↑↓ 已经够了。
3. **右键点在哪一行**：点在已选中的行上，选中不变，菜单作用于全部；点在没选中的行上，先改成只选这一行。和 VS Code、IDEA 一样。
   - **光标那一行不加标记**（2026-10-19，同 IDEA）：IDEA 的提交列表只用「有没有焦点」决定选中行的底色深浅，光标所在行看不出来，Shift+↓ 从最后点的那行出发。否决照 VS Code 给光标行加边框：多选几乎都用鼠标，用不上；真要加只改样式。
4. **右栏跟着整个选中走**（2026-10-19 项目负责人定）：多选时照 IDEA 把几条提交的改动按文件合并显示，详情区列出每一条——**不在本阶段做**，进需求池（`product/backlog.md`「Log」，难度写在那一条里）。diff 本来就跟着右栏里选中的文件走、不跟提交列表（`product/features/trees.md`「打开 diff」），合并显示做出来以后它自然跟着变，不用另定。
5. **本阶段多选时的右栏**：上面的文件区中间写一行灰字 `3 commits selected`，下面的详情区留空，不取文件；选中变回一条时照现在重取。
6. **刷新、过滤之后**：选中的提交还在列表里就留着，不在了就去掉。一条都不剩时照现在的单选规则：刷新后选 HEAD 所在的提交，过滤后什么都不选。
7. **选中不设上限**（2026-10-19 项目负责人定）：IDEA 只取前 1000 条。我们的列表本来最多一万条，命令行太长的问题由第三节第 12 条解决，没有别的地方需要这个上限。

## 二、右键菜单

8. **多选时菜单里有什么**：

   | 菜单项 | 多选时 |
   |---|---|
   | Copy Hash | 有。完整 hash 按列表顺序，用空格隔开（同 IDEA） |
   | Cherry-Pick、Revert | 有；选中里有合并提交时没有（第 9 条） |
   | Rebase onto Here、Reset Current Branch to Here…、Edit Commit Message…、New Branch from Here… | 没有：都只能对一条做 |

   - 不能用的项**直接不出现**，不置灰（2026-10-19 项目负责人定）：右键菜单「不可用的项不出现」本来就是定了的做法（`tech/decisions.md`「右键菜单的排序与分隔」）；原生菜单能置灰，但写不了为什么灰。
   - 菜单文字不随数量变，不写 `Cherry-Pick 3 Commits`：选了几条自己看得见。
9. **选中里有合并提交时不给 Cherry-Pick、Revert**（2026-10-19 项目负责人定）：git 在一串里碰到合并提交会报错退出，但它前面的提交已经摘过来了，还留下一个「操作进行中」的标记。这时我们的面板认为什么都没在进行，git 却认为有：`git status` 说 cherry-pick 在进行，`git switch` 被拒，再来一串 cherry-pick 也被拒，只有单条 cherry-pick 照常成功（git 2.43 实测）。用户会卡在一个看不见的半截状态里。单选时不受影响：单条合并提交 git 直接拒绝，什么都不动（实测），照旧显示 git 的报错。
10. **复制快捷键照 IDEA：一条一行**（2026-10-19 项目负责人定，单选多选一样）：每条一行，写说明的第一行、作者名字、日期，用空格隔开；多选时按列表顺序一行一条。同 IDEA 的 `VcsLogGraphTable.performCopy`（看得见的各列用空格连，一行一条）。日期仍写绝对时间：贴出去的文字不该写「5 minutes ago」。这改掉了现在单选时的格式（完整说明加 `Author:`、`Date:` 两行），因为一条一行贴一串提交更好看。否决多选时每条都是整段：贴出来又长又散。

## 三、一组操作停在一半

11. **顺序**：cherry-pick 从旧到新，revert 从新到旧（都同 IDEA）。按提交在列表里的顺序算，不按点选的先后。
    - 状态栏：一条时照旧 `Cherry-picked 1a2b3c4`；多条时进度写 `Cherry-picking 3 commits…`，完成写 `Cherry-picked 3 commits`、`Reverted 3 commits`。
12. **整串交给一条 git 命令**（2026-10-19 项目负责人定）：`git cherry-pick --stdin`，把 hash 一次交给 git，由 git 自己记住做到哪了。停在冲突时就是现在的「停在半路」（`product/features/conflicts.md`），继续、放弃的按钮都不用改：
    - **继续**：接着做剩下的。
    - **放弃**：回到整串开始之前，已经摘过来的也一起撤掉（实测）。这是代价：摘了九条、第十条冲突，点放弃就十条全没了。
    - 否决照 IDEA 我们自己一条一条地循环：停在冲突时，剩下哪些只有我们知道；点继续之后还得我们接着循环，而现在的继续只是交给 git 的 `--continue`。
13. **某条变空了：自动跳过**（2026-10-19 项目负责人定，同 IDEA）：「变空」是这条提交的改动当前分支上已经有了（比如以前摘过），再摘一次什么都不变。git 会停下来让人选跳过还是留一条空提交，这时点继续过不去（git 2.43 实测）。
    - 做法：开始执行后碰到变空的，自动跳过、接着做下一条；完成消息写上跳过了几条，`Cherry-picked 1 commit, skipped 1 already applied`。IDEA 同样记进 `alreadyPicked` 后接着做（`GitApplyChangesProcess.kt`）。
    - 单条也走这条路，改掉现在的行为：现在单条变空时停在半路，面板只有继续和放弃，继续过不去，只能放弃。
    - 否决照现在停下、等需求池里的 Skip 按钮：一串里只要有一条以前摘过，就卡住。否决留一条空提交（`--keep-redundant-commits`）：历史里多出没有内容的提交。
    - 「解决冲突后点继续，结果变空」仍照现在处理（git 报错，Skip 在需求池）。

## 不做

14. Squash、批量 Drop（要对话框或 `rebase -i`，单独成阶段）；比较两条提交（要新的比较视图）；Stash 列表多选（IDEA 也只能单选）；Log 右栏文件的多选（现在只有双击打开，没有能批量做的事）。

## 四、技术方案

### A. 选中规则：`logic/` 里一组纯函数

- 选中状态是一个值：选中的 hash 集合、锚点、光标所在行。第 2、3、6 条的每种按键、点击、刷新各是一个纯函数：输入行的顺序和这次的动作，输出新的选中状态。它不认识提交还是树节点，第 15 阶段的树直接用。Vitest 测。
- 选中状态由 `LogApp.vue` 持有（现在就是它持有一个 hash，传给 `CommitList.vue`）。不存进 `viewState`：现在的单选也不存。
- 只存 hash，不随行数生成 DOM；一行高不高亮，看它的 hash 在不在集合里。

### B. 右键菜单怎么拿到整组（2026-10-19 实测可行）

**现在怎么工作**：每一行身上带一份 JSON（`data-vscode-context` 属性），写着「我是哪条提交、能不能改说明」。右键时 VS Code 从被点的元素往外层找，把找到的几份合起来，用它决定菜单里出现哪几项（`package.json` 里每项的 `when` 条件），点了某项再把这份 JSON 交给扩展（`extension/src/vscode/menu.ts`）。**问题**：它只看被点的那一行，别的选中行它看不见。

**做法：右键那一刻抢先写上去。** 行上不再带 JSON。列表容器收到 `contextmenu` 时，先按第 3 条更新选中，再算出这次的 JSON，**直接改 DOM** 写到容器上。右键事件从被点的行往外传，先到我们的容器、后到 VS Code 挂在最外层的监听，VS Code 读的时候已经是新写的。
- **实测**（2026-10-19，F5 调试窗口，提交列表）：行上去掉 JSON、只在右键时写容器后，菜单项照旧；交替右键两条提交、各点 Copy Hash，粘出来的各是各的；能改说明和不能改说明的两条交替右键，Edit Commit Message… 每次都跟着变，不慢一拍；空白处右键不出我们的菜单项。
- **未测**：菜单键、Shift+F10。Mac 上没有菜单键，Shift+F10 要按 fn；要支持键盘弹菜单，还得在按键时记一下「这次是键盘弹的」，否则和右键点在列表空白处分不开（实测时混过一次）。现在不支持，和改之前一样。
- 直接改 DOM，不经 Vue：Vue 把改动攒到稍后才写进 DOM，赶不赶得上 VS Code 读，取决于浏览器内部的时机，读代码的人看不出来。
- 依据：GitLens 的 webview 也这么做（`.notes/vscode-gitlens-main/src/webviews/apps/shared/components/tree/gl-file-tree-pane.ts` 的 `onContextMenuEnrichSelection`）。
- 否决**自己画菜单**：自己画就能像 IDEA 一样，菜单要弹时直接读选中，没有先后顺序的问题，还能去掉「第二个入口」。但它只能画在 webview 那块矩形里，Log 是底部面板，常常放不下八九项的提交菜单；外观、键盘、点到 webview 外面时关菜单、读屏器都要自己做。抢先写已经实测可行，就不换。哪天原生菜单不够用了（比如要写置灰的原因），再回来重新定。
- 否决每一行都带上整组：选中一变，每个可见的选中行都要重写一遍整串；Ctrl+A 一万条时是几十 MB。
- 否决点了菜单项以后再回头问页面选了什么：已经否决过（`tech/decisions.md`「原生右键菜单是协议的第二个入口」）——只解决得了点下去做什么，解决不了菜单里出现哪些项，而且要求页面还开着。

**菜单项怎么定义：每个菜单项一个键**（2026-10-19 项目负责人定，所有树和提交列表共用）

右键时，页面对每个菜单项算出「这次要作用于哪些东西」，算得出就写一个键，算不出就不写：
- 键在，菜单项就出现；键的值就是交给扩展的参数。`package.json` 的 `when` 一律是 `webviewId == … && dummyGit.<这一项的键>`。
- 扩展的菜单命令只取自己那个键，过同一张参数校验表（C.1），交给处理函数，自己不再判断。
- 竖按钮、工具栏按钮用同一个菜单项定义，「能不能做、对谁做」只有一份。
- 依据：IDEA 每个菜单项的 `update()` 与 `actionPerformed()` 读同一份选中、用同一段判断。VS Code 弹菜单时不回来跑我们的代码，所以改成右键那一刻由页面替每一项算好。现有的 New Branch from Here… 就是这样（`when` 是 `dummyGit.start`，竖按钮用同一个 `startOf`），推广到全部。
- 否决「名单 + 节点类型 + 开关键」：每一项真正要动的是名单的一部分（Delete 跳过当前分支），挑这一部分的规则页面要写一份（决定出不出现），扩展又要写一份（决定动谁）；现在 Delete 的 `when` 和竖按钮的 `deleteTargetOf` 就是两份。而且 `when` 是没人测的字符串。

**一个菜单项写三样东西**：
- **看法**：「展开看」是选中的叶子加上选中目录下面列出的全部叶子，去掉重复（同 IDEA `VcsTreeModelData.selected`）；「原样看」是点中的节点本身，目录就是目录（同 `exactlySelected`）。目录只是归类时用展开看（分支目录、Commit 面板的目录、提交列表没有目录）；目录本身就是对象时用原样看（以后的「Fetch 这个远程」「这个目录的历史」）。同 IDEA 改动树与 VS Code SCM 的目录（展开）、GitLens 的 Stage Directory 与 IDEA 的远程名（对象）。
- **单个判断**：这一个东西能不能做。
- **整体条件**（可选）：对整体的要求，比如「正好一个」（Reset、Reword）、「至少两个且相邻」（以后的 Squash）。只能单选和只能多选是同一回事。

**框架怎么算**（`logic/` 里一个共用函数，配测试）：按看法取出东西 → **每一个都通过单个判断**，否则不出现 → 通过整体条件，否则不出现 → 出现，值是这些东西。
- **全部严格**（2026-10-19 项目负责人定）：不跳过任何东西，点了就是全做。否决「直接选的严格、目录带进来的只取能做的」：要给每一项带上「怎么进来的」标记，规则多一层，参照里也没有人这么做。代价：一个目录里只要有一个做不了的，整组就没有这一项（右键 `Local` 没有 Delete，因为里面有当前分支）。

```jsonc
// 提交列表，选了三条
{ "dummyGit.repo": "/r", "preventDefaultContextMenuItems": true,
  "dummyGit.copyHash": ["1a2b…", "3c4d…", "5e6f…"] }
  // Reset、Edit Commit Message 的整体条件是「正好一个」，这里没有它们的键

// 右键一条能改说明的提交
{ "dummyGit.repo": "/r", "preventDefaultContextMenuItems": true,
  "dummyGit.copyHash": ["1a2b…"], "dummyGit.cherryPick": ["1a2b…"], "dummyGit.revert": ["1a2b…"],
  "dummyGit.rebaseHere": "1a2b…", "dummyGit.resetTo": "1a2b…", "dummyGit.reword": "1a2b…" }
```

- **要先实测**：键的值是列表（或字符串）时，`when` 里只写键名能不能当作「有」。VS Code 读这一段的代码不在本地。不成立就每一项另写一个布尔开关。
- **未测**：Cmd+A 一万条时，提交列表三个批量项各带一份 hash 列表，估计每次右键约 1.3 MB。
- ⌘C 复制不是菜单项，直接用原样看。

### C. 协议：命令改成收一个列表

- `cherryPick`、`revert` 的参数 `hash` 改成 `hashes`。单个就是只有一项的列表。否决另加 `cherryPickMany`：两条命令回答同一个问题（D.6d），单条那条不是非有不可的。
- 菜单命令取自己那个键的列表，和页面按钮过同一张参数校验表（C.1）：列表非空，每个 hash 照旧校验。
- Copy Hash 仍是 `copyText`，扩展把 hash 用空格连起来。
- 顺手修：`shared/src/protocol.ts` 里 `cherryPick` 的说明注释错挂在了 `resetTo` 上面。

### D. 执行与日志

- `git cherry-pick --no-edit --stdin`、`git revert --no-edit --stdin`，hash 从标准输入按第 11 条的顺序喂进去，git 照这个顺序做、不重排（git 2.43 实测）。用标准输入不用命令行参数：Windows 的命令行最长 32767 个字符，大约八百个 hash 就超了。**git 2.25 上没测过**，实现那步用 `pnpm test:old-git` 确认，不行就改回命令行参数，并回头重新定第 7 条要不要设上限。
- 变空（第 13 条）：结果是「变空」，就跑 `cherry-pick --skip`（git 2.23 起有）再看，直到做完或停在冲突。
- 有合并提交时由页面去掉菜单项（第 9 条），扩展不再查一遍：边界之内信任类型（C.2），漏过去 git 也会拒绝。
- 日志：参数是列表时 `brief()` 已经会列前 3 个加总数，不用改。

## 五、实现顺序

每步一个概念，`pnpm check` 通过、手动看过、项目负责人确认后单独提交。

1. **右键菜单改为右键时写在外层**（仍是单选，JSON 的内容不变）：提交列表和 `Tree.vue` 都是行上去掉 JSON，右键时写到容器上；菜单和现在完全一样。测试：由被点的行算出容器上写什么（点在行上、点在空白处、点在没有菜单的行上）。手测：第四节 B 实测的那几种。
2. **选中规则**：`logic/` 里的纯函数与测试，不接界面。
3. **提交列表接上多选**：点选、键盘、右键改选中；刷新、过滤后的收缩；右栏 `N commits selected`（第 5 条）。
4. **菜单框架**：先实测键的值能不能直接当 `when` 的条件（第四节 B）。再写两种看法与共用的计算函数，提交列表的 6 项（Copy Hash、Cherry-Pick、Revert、Rebase onto Here、Reset、Edit Commit Message）改成「每项一个键」；只能对一条做的整体条件是「正好一个」，Cherry-Pick、Revert 这一步也先是「正好一个」。多选时出现 Copy Hash。树的菜单项第 15 阶段再改，其间两种写法并存。测试：由选中算出各项的键。
5. **复制改成一条一行**（第 10 条）：⌘C 单选多选都是 `说明第一行 作者 日期`；`product/features/log.md` 同步改。
6. **批量 Cherry-Pick、Revert**：协议改成 `hashes`，`--stdin`，顺序，变空；去掉「正好一个」，单个判断改为「不是合并提交」（只有一条时照旧交给 git 报错，第 9 条）。测试：真 git 下的顺序、变空、停下后继续接着做剩下的；`pnpm test:old-git`。
7. **验收**：要核对的条目勾过；验收句手动走一遍；并进 `product/features/log.md`、`product/features/trees.md`，删掉本文。
