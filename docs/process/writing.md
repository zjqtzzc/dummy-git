# 文档与注释怎么写

> 写或改 `docs/` 下的文档、代码注释时照这里做。写法变了就改本文。

## 文档

- **一个事实只有一处权威。** 其他地方写「见 `<文件> §<节>`」，引用要具体到节。
- **只写对当下仍起指导作用的。** 过时了直接删，不留墓碑，不写「原来是 X，现在改成 Y」，也不解释为什么删：git 历史里都有。
  做减法要做到文档本身：一次以「清理」为目标的修改，净行数应该是减少的。
- **每篇开头一句话**：这篇回答什么问题，什么时候要改它。
- **决定要写否决了什么**（D.4）：读起来合理的理由，和真正的理由一模一样；能防止下一个人重走一遍老路的，是「试过 X，因为 Y 不行」。
- **「项目负责人定」带日期**，比如「（2026-10-16 项目负责人定）」。旧文档里写成「用户定」的，意思一样。
- **文档中文，界面文字英文**。

## 写在哪

| 内容 | 放哪 |
|---|---|
| 违反了就打回的规则 | `CLAUDE.md` |
| 做事的方法 | `process/` |
| 有哪些阶段、各做什么 | `product/roadmap.md` |
| 以后可能做的 | `product/backlog.md` |
| 定了永远不做的 | `product/never.md` |
| 一个功能现在是什么样、为什么 | `product/features/<功能>.md` |
| 技术选型 | `tech/architecture.md` |
| 跨功能的决定 | `tech/decisions.md` |
| git 的坑、组件的坑、做事的教训 | `tech/traps.md` |
| 实测的数字（写明在什么上测的、怎么再测一次） | `tech/performance.md` |
| 正在做的阶段的设计稿 | `phases/phase-NN.md`，阶段结束时并进 `features/`（`workflow.md` §2） |
| 参照项目的笔记 | `refs/` |

## 代码注释

规则见 `CLAUDE.md` F。补几条做法：
- 道理写在注释里。以前要「见某文档」才能讲清楚的，把要紧的那一两句搬进注释，其余的不要。
- 坑写在踩坑的那行代码旁边：现象、原因、为什么这么绕开。在哪个 git 版本上实测过，也写上。
- 写「为什么这样、不那样」时，把否决的那条也写上（「否决 `-m` 单用：每个父提交各输出一遍」），免得下一个人改回去。
