# 手动测试（F5 调试窗口）

> F5 打开的调试窗口里是什么仓库、怎么准备现场、手测怎么交接。加场景、改机制时改本文。自动测试见 `process/testing.md`。

## 机制

- 调试窗口打开的是本仓库旁边的**独立仓库** `../<目录名>-debug`，每次 F5 由 preLaunchTask 跑
  `pnpm debug:setup`，按 `.tmp/debug-scenario`（gitignore）记下的**当前场景**删掉重建。
- 选场景 / 换场景：`pnpm debug:setup <场景名>`，再按 F5。
- 重建只清空目录里的东西、不删目录本身：调试窗口开着时，它对工作区根目录的文件监听挂在这个目录上，
  目录一删就没了。用户实测（2026-10-15）：调试窗口开着时换场景，Log、Commit 面板与资源管理器都跟着刷新，不用关窗口。
- 场景 = `scripts/debug/scenarios/<场景名>.mjs`，导出 `build(g)`；`g` 只有 `write` / `remove` / `git` / `gitInput` / `gitMayFail`。
- 身份与时间用本机真实配置（不像 fixture 那样固定），贴近日常使用。

## 交接约定

agent 把一步交给用户手测前：
1. 选好或写好场景，跑 `pnpm debug:setup <场景名>`，看它打出的 `git status` 确认现场对了。
2. 交接消息写「已跑 debug:setup <场景名>，按 F5，看这几点：……」。看哪几点写成编号清单，每条写「做什么 → 应该看到什么」。
   **看哪几点只写在交接消息里**，不写进场景——它随步骤变，不属于场景。
3. 只改纯逻辑、界面没有变化的步骤不交给用户手测，交接消息里说明「这一步不需要 GUI 测试」。
4. **F5 尽量少**（2026-10-21 项目负责人定）：能一起测的攒到一起测。写阶段稿的实现顺序时就把要手测的几步排在一起，中间几步只交测试结果；交接消息写明这次一并看了哪几步。

## 固定场景

手测先从这几个里挑，每个现场有什么写在它的文件头里：

| 场景 | 测什么 |
|---|---|
| `everyday` | 没有停下的操作：Log、分支树、Stash、Commit 面板各种改动、Reset、Reword、各处右键；能当场造出 cherry-pick / merge / rebase / stash 取回的冲突 |
| `remote-sync` | 本地裸远程：Fetch、Update（单个、批量、分叉）、Push 对话框、Checkout 远程分支 |
| `merge-stopped` | 停在半路的 merge：七种冲突、冲突组标题行、各种解决办法与批量 |
| `graph-large` | 一万条以上的提交：图与性能（`tech/performance.md` 的数字在它上面测） |

## 加场景

- 新功能要手测的形态，**先补进固定场景**（同类的多种形态各造一个，外加不该受影响的对照文件），不另起一个。
- 放不进去时才新建临时场景（`CLAUDE.md` D.6a：有一步手测要用它时才加），阶段验收时删掉（`workflow.md` §2「结束」）。
- 要远程的场景自己在目标目录里建一个本地 bare 远程，不碰任何真实远程。
- 场景造出什么现场，写在它自己的文件头里；上面的表只写它测哪一类，不抄现场。临时场景看 `scripts/debug/scenarios/` 目录。
