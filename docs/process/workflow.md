# 开发流程

> 一件事从提出到做完，按什么顺序走、每一步交出什么。
> 违反了就打回的硬规则在 `CLAUDE.md`（下面写作 D.3、D.6 等），这里讲怎么做。流程变了就改本文。

## 1. 三大步，每一步落成文件才算结束

需求 → 技术选型 → 细节加实现。

| 步 | 交出什么 |
|---|---|
| 需求 | `product/roadmap.md` 里一个阶段的验收句，或 `product/backlog.md` 里的一条 |
| 选型 | `tech/architecture.md` 的一道题：选了什么、否决了什么 |
| 细节加实现 | `phases/phase-NN.md`，然后是一串小提交 |

提问之前先判断这个问题属于哪一步：不属于当前这一步的不问，记下来，到那一步再问。

## 2. 一个阶段

**开始**
1. 从 `product/backlog.md` 里挑出来，在 `product/roadmap.md` 的阶段表里加一行验收句，那条需求从 backlog 移进这个阶段。
2. 照 `templates/phase.md` 建 `phases/phase-NN.md`。先把「要核对的条目」列出来：这个阶段的需求条目，加上 `tech/architecture.md` 里这个阶段第一次用到的题目。

**定细节**
- 交互细节逐条定。每条写清楚「已定（日期）」，否决过的做法写在同一条里，并写明为什么否决。
- 先看参照项目（多半是 IDEA）是怎么做的，**到源码里核对**，不凭印象。要不要搬过来，按 D.6(c) 判断。
- 有约束挡住了最简单的做法：把「最简单的做法 + 要放宽的约束 + 代价」摆给项目负责人定（D.6e）。方案先实测，再写进设计。
- 最后写实现顺序：每步一个概念，写得出每一步交出什么。

**先对齐方案，再动手**（2026-10-21 项目负责人定）：任何改动（新功能、改 bug、换做法）先把方案摆出来，和项目负责人取得一致后才写代码。做到一半要求变了，先停下、撤掉没提交的改动，重新对齐方案，不在旧方案上接着改。项目负责人说过「直接提交」的，指的是方案定了以后不必每步再问，不是可以跳过对齐方案。

**实现**：按实现顺序，一步一件小事（D.3）。每一步怎么做见第 3 节。

**结束**
1. 「要核对的条目」逐条勾过；验收句手动走一遍；`pnpm check` 通过。
2. 交互细节并入 `product/features/` 里对应的功能文档；只关乎这个功能的决定，也随它一起并过去。然后删掉这份阶段稿。
   `features/` 只描述现状，读者不用再分辨哪句话已经过时。阶段稿的过程留在 git 历史里。
3. `product/roadmap.md` 的阶段表里记下这个阶段已完成。

**不悄悄推翻已定设计**：实现时发现设计要改，就明说，并在同一个提交里改文档。

## 3. 每一小步

1. **只改一个概念**，说明为什么这么改。
2. **测试**：新增的行为配测试，判据见 `testing.md`；一跑就能看出来的问题不写测试。
   **变异确认**：临时把守卫改坏（删掉一行、换个条件），看测试确实变红，再改回去。不红就说明这条测试没测到要测的东西。
3. **检查**：`pnpm check`。在 VS Code 的终端里跑时要去掉继承来的 askpass 变量（见 `tech/traps.md`）。
   - 动了 git 命令行，再跑一次 `pnpm test:old-git`（最低版本 git 2.25 上的测试）；
   - 新写或改过的脚本（包括 `scripts/` 下的调试场景）同样要过检查，lint 会查到 `scripts/`。
4. **手测交接**：界面有变化的步骤交给项目负责人手测，约定见 `manual-testing.md`。
   F5 会先重建调试仓库，所以要在调试窗口起来**之后**再做的手动改动（比如在终端里改一个文件），交接时要写明。
5. **提交**：检查通过、项目负责人确认后，单独提交，再开始下一步。不要让几步的改动在同一个文件里交叉，事后很难拆开。
   提交信息写 `feat(阶段N-M): <这一步做了什么>`；修 bug 写 `fix:`，杂项写 `chore:`，文档写 `docs:`。

## 4. 设计时的几条做法

- **一定会做、而且现在就影响结构的，低成本先占位**（D.6a 的例外）。比如 Commit / Stash 的切换栏，第二个模式还没做，切换栏就先摆上。
- **开发中的控件不做临时置灰**：还没接上功能的控件放着就行，点了没反应。设计里规定的置灰条件，到接上功能的那一步照做。
- **前端控件等用多了再抽**：只有一两处用到的，先写在原地；出现第三处相似写法时，抽成 `webview/src/ui/` 下的组件。现成的组件先用现成的。
- **提示文字先用 git 原文**：git 已经说清楚的，不自己另写一句。
- **讨论合并时从文件讲起**：先讲「这个文件现在是什么样、合并后应该是什么样」；暂存区只是实现手段，不作为代价摆给人权衡。
- **默认做减法**：两个方案差不多时，选东西少的那个。没有消费者的不加（D.6a），删掉之后没有任何测试会失败的不留（D.6b）。

## 5. 出问题时

1. 先拿日志：「输出」→ Dummy Git。日志怎么记见 `CLAUDE.md` G。
2. 先看开头那行运行环境：git 版本、远程类型（容器、SSH、WSL）、系统。只在某些机器上出的问题，多半出在这里。
3. 怀疑是 git 版本差异的，用 `pnpm test:old-git` 复现；确认了就记进 `tech/traps.md`。
4. 用对方的真实数据跑一遍我们的代码，再下结论；不靠推测。
