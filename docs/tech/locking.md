# 锁、占用与处置

> git 的锁被占用时（别的 git 进程、我们自己的命令）怎么分类、怎么处置。调度与锁的做法变了就改本文；`core/operation.ts` 的文件头指向这里。

## 1. 占用有三种，处置各不相同

| # | 占用来源 | 我们知不知情 | 处置 |
|---|---|---|---|
| ① | **我们自己的命令并发** | 完全知情（我们发起的） | 写命令排队，用户看不到任何异常 |
| ② | **外部进程，瞬时**（用户终端里的 `git commit`） | 命令失败后才知道 | 报一个说得清楚的错，用户自己解决 |
| ③ | **陈旧锁**（git 崩溃后残留的 `.git/index.lock`） | 与 ② 无法区分 | 不专门处理；git 原文里的指引兜底 |

分开看就明白：① 根本不该走错误路径，③ 重试一万次也没用，只有 ② 需要一条可操作的消息。

## 2. ① 我们自己的并发：排队

两条道、`LockPolicy` 三态、含网络的组合在网络处拆开，见 `tech/architecture.md` 第 12 题。这里只补一条：

- **无限期排队，不设超时**：超时了也没有更好的处置。本地道里全是毫秒到秒级的本地命令；
  残余风险只有 pre-commit 钩子挂死，进程层已支持取消，真需要时接线即可。

## 3. ② 外部瞬时占用：报错，不重试

- **不自动重试**：会掩盖用户该知道的事（自己在两处同时操作），而且是对一个正在变化的仓库重试，即使成功也是在中间状态上操作。
- **不做重试按钮**：只要失败不清空状态，用户重新点一次的成本几乎为零。
- 消息要**说出不可见的原因**：用户看到 `fatal: Unable to create '.git/index.lock'` 不会想到是自己终端里那条命令。
  `RepositoryIsLocked` 的存在就为这个（原始 stderr 的第一行会误导，有用的解释在第三行）。
- **失败不清空状态**：提交失败 → 说明与勾选原样保留；任何写操作失败 → 面板停在失败前的状态。这比任何重试机制都重要。
- 会撞锁的全是写命令（实测：持有 `index.lock` 时 `status` / `log` / `for-each-ref` / `rev-parse` / `diff` / `fetch` 全部照常），
  而写命令由用户主动触发，所以撞锁 ⇒ 用户同时在两处写。

## 4. ③ 陈旧锁：不专门处理，永不自动删

- 从外面看与 ② 完全一样，git 自己也分不出来（它的消息用的是 `seems to be` / `may have crashed`，把判断交给用户）。我们不可能比 git 更清楚。
- git 的完整 stderr 里已经带了指引（`remove the file manually to continue`），错误关口把 stderr 全文写进输出面板，指引就在那里。
- **永不自动删锁文件**：猜错（进程其实还活着）就放行了第二个写进程，可能写坏暂存区。省一次 `rm`，换损坏仓库的风险，不划算。

## 5. 不把 `.git/index.lock` 当状态源

不用 watcher 监听它来显示「仓库被占用」：正常操作下每条写命令都会毫秒级建了又删，是纯噪声；
陈旧锁还会让这个状态永久卡住。保持反应式（命令失败才知道），watcher 过滤掉所有 `*.lock`。

## 6. `GIT_OPTIONAL_LOCKS=0` 的三个作用

实测持有 `index.lock` 时 `git status` 照常成功——它只机会性取锁，取不到就跳过 stat 缓存回写。所以这个变量**不是**为了避免失败，而是：

1. 避免那次回写触发我们自己的 watcher → 刷新 → 又跑 status 的回路；
2. 避免撞外部锁（次要）；
3. 让 `status` 可以不进写队列——它证明了自己不写 index，才能归 `LockPolicy.None`。

三条都要记住，否则有人看到「status 本来就不会失败」就把它删了。

## 7. 外部命令结束后必须刷新

用户在终端 `git commit` 之后仓库已经变了。同一个外部写操作，既可能造成一次撞锁，也一定造成一次状态变化；后者靠 watcher 感知。
