## 结论

### 1. Log 挂在底部面板

**选**：在底部面板区注册一个自己的视图容器，里面放一个 WebviewView。左中右三栏都在这一个 webview 里。

**否决**：
- 编辑区的 WebviewPanel。现在的代码就是这样，只用于地基期测试。
- 三栏拆成同一容器里的三个视图。VS Code 会免费提供分隔条和栏宽记忆，但三栏之间的联动（点提交 → 右栏换文件）要绕扩展一圈，一次选中要走两趟消息，还得起三个 webview。
- 原生 TreeView。画不出 Message / Author / Date 三列的表格。

**带来的约束**：webview 的页面可能重建（窗口刚打开、VS Code 回收了隐藏的页面），握手的换代机制为此准备。面板收起时保留页面（`retainContextWhenHidden`，2026-10-21 改：不保留时每次展开都黑屏几百毫秒，见 `tech/performance.md` §5.1），隐藏期间的广播攒着、重新可见时一次发出（`ipc/hiddenBuffer.ts`）。

### 2. Commit 面板用侧栏的 WebviewView

**选**：侧栏注册一个 WebviewView。文件树、复选框、提交说明框、Commit / Stash 切换、进行中横幅，都在这一个 webview 里自己写。树组件和 Log 右栏共用一份。

**否决**：
- 原生 TreeView 加 SCM 输入框。输入框只有注册成源代码管理提供方才有，注册后会和自带的 Git 并排出现在「源代码管理」视图里。
- 原生 TreeView 加一个只放输入框的小 webview。同一块面板拆成两个视图，勾选状态和提交动作要在两边同步。
- 原生 TreeView 白给的复选框和目录联动，抵不过横幅、模式切换、冲突组没有复选框这些它做不出来的东西。

**参照**：GitLens 的提交入口同样全在 webview 里：自写的树、复选框、提交框、合并 / rebase 状态横幅；原生 TreeView 只用来浏览。

**代价**：文件图标（第 5 题）和键盘操作要自己做。

### 3. 前端栈：Vue 3 + TypeScript + Vite + vscode-elements

**选**：
- 我们自己的界面（Log 面板、Commit 面板、提交列表）用 Vue 3 单文件组件写，脚本部分一律 TypeScript，Vite 打包。
- 控件用 vscode-elements：文字按钮、输入框、分隔布局、进度条。外观和键盘操作跟 VS Code 一致。
- **工具栏上的图标按钮一律用 `webview/src/ui/ToolButton.vue`**，不手写 `<button>`：悬停、焦点框、置灰、提示文字只在这一处。点了弹出选单的用 `ui/MenuButton.vue`（包着 `ToolButton`，右下角带小三角，选单是 webview 里的浮层，`product/features/menus.md`）。例外两处，都不是工具栏按钮：冲突组标题行的继续、放弃（带颜色的实心操作按钮，`product/features/conflicts.md`），过滤栏里生效条件后面的 ×（文字按钮的一部分）。右键菜单不用它，用 VS Code 原生的（`webview/context`，`tech/decisions.md`「右键菜单：每个菜单项一个键」）。Vue 对自定义标签是正式支持，事件直接写 `@vsc-split-layout-change`。
- 图标三种来源（`webview/src/logic/icons.ts`）：`@vscode/codicons`（vscode-elements 本来就依赖它）；codicon 没有的、或 IDEA 的更好认的，自己画成线条（规则见 `tech/decisions.md`「图标」）；文件图标用打包的 Seti（第 5 题）。
- 样式只用 VS Code 注入的 `--vscode-*` 主题变量。

**vscode-elements 不够的地方**（2.5.1 版实测）：
- `vscode-table` 没有虚拟滚动，几万条提交撑不住。IDEA 的 Swing 表格天生只画可见的那几行，浏览器里每一行都是真实的 DOM 节点，这件事得自己做。提交列表自己写，见第 9 题。
- `vscode-tree` 只给一个 22px 的图标位、不发展开事件、行的点击与焦点在它内部、没有虚拟滚动，复选框放不进去。所有树改用自己画的基础组件 `tree/Tree.vue`，外观与键盘照 VS Code 原生的树（`product/features/trees.md`）。
- `vscode-split-layout` 一次只分两块，三栏嵌套两层。
- `vscode-toolbar-button` 只认 codicon，也没有 `disabled`：图标按钮自己做（`ui/ToolButton.vue`），样式照它。
- `vscode-checkbox` 在暗色主题里和背景几乎一样，勾太细，样式也改不进它里面：**复选框一律用 `webview/src/ui/CheckBox.vue`**（树里每一行的、Commit 面板的 Amend……），不用 `vscode-checkbox`，也不各自画。外观照 IDEA 新界面：没勾是边框比背景明显的圆角方框，勾上、半勾填满主按钮的蓝，里面是白色的勾或横条，线宽 2（2026-10-21 项目负责人定）。

**工具链要跟着改**，否则 `.vue` 文件会漏出类型纪律：
- 类型检查从 `tsc` 换成 `vue-tsc`。
- 禁止 `as` 的检查脚本目前只扫 `.ts` / `.tsx`，要扩到 `.vue` 的脚本块。
- Biome 对 `.vue` 的覆盖程度，改工具链时实测再定。

**否决**：
- React。hooks 有反直觉的坑（回调读到旧值、effect 依赖），用自定义标签的事件要单独处理。它唯一的硬优势是 TSX 不用改工具链。
- Lit。和 vscode-elements 同一套写法，但学到的东西在别处用得少。
- 不用框架，只用 vscode-elements 加手写 DOM 更新。状态变化全靠手写同步，最容易漏。
- 微软的 Webview UI Toolkit。已停止维护。

### 4. 各块 webview：一份打包，按视图挂根组件，互不通信

**选**：
- 同一个 Vite 工程、一份 `webview.js`。扩展在 HTML 的 `#root` 上写视图 id（`data-view`，即 `package.json` 里的 id），`main.ts` 按它查表挂 Log 或 Commit 的根组件。树组件、协议客户端共用。
- 两块 webview 之间不直接通信。每块各配一个 Router，各自订阅仓库的分域过期事件。提交后 Log 刷新、Log 上 merge 停下后 Commit 面板出横幅，都靠这条路。
- 对话框（第 10 阶段起，`product/features/dialogs.md`）是开在编辑器标签页里的另一块 webview，同一份打包，按视图 id（`dummyGit.push`、`dummyGit.reword`）挂根组件。它针对的东西（推送对话框是分支名，改说明是提交 hash）写在 HTML 的 `data-subject` 上，和视图 id 一样是页面身份的一部分。也配一个 Router，但不订阅仓库的广播（内容打开时取一次）；关自己、做完关掉都经扩展（`vscode/dialogPanel.ts`）。
- 界面自己的状态（勾选了哪些文件、写到一半的提交说明）放在各自 webview 里，同时存进 VS Code 的 `setState`，视图收起再打开时恢复。

**否决**：
- 两个入口（第 2 阶段前的定案，2026-09-30 改掉）。当初的两条理由没有兑现：「到处是『我是哪块』的分支」——实际只有 `main.ts` 一张两行的表；「Commit 面板连带加载 Log 的代码」——从本地磁盘读两百来 KB，感觉不到。换来的是多入口配置、共享块拆分、扩展按视图挑脚本与样式。
- 拆成两个包。共用组件和构建配置要重复或再抽一个包。
- 两块 webview 经扩展转发、直接同步状态。扩展已经是状态权威，再加一条通道就是两个东西回答同一个问题。

**参照**：IDEA 的 Log 和 Commit 界面同样互不引用。共享的是项目级服务（`GitRepository`、`ChangeListManager`、`GitStashTracker`、`VcsLogData`），仓库状态变化通过消息总线 `GIT_REPO_CHANGE` 广播，十几处界面各自订阅。

### 5. 文件图标：打包 Seti 快照

**选**：
- 文件按类型显示图标，用打包进插件的 Seti 快照：Seti 字体加一张「文件名 / 扩展名 → 字形和颜色」的映射表。
- 快照由脚本从 VS Code 自带的 `theme-seti` 扩展生成，VS Code 更新了可以重跑。
- 按 Seti 主题文件的规定，字形放大到 1.5 倍。
- 目录、展开箭头等其余图标用 codicon。

**否决**：
- 读取用户当前的文件图标主题。webview 拿不到；要做就得找到主题所属的扩展、解析它的主题文件、再把它的字体或图片放进 webview 的资源目录，每种主题格式都可能不同。
- 手工提取、不可重做的快照。VS Code 更新 Seti 后没法同步。
- 只用 codicon 的通用文件图标。需求要按类型区分。

**参照**：GitLens 和旧工程都打包了 Seti 快照。GitLens 用脚本生成映射表；旧工程手工提取，字体以 base64 嵌进 JSON。

### 6. VS Code 版本：最低 1.85，面向最新版

**选**：清单里写 `^1.85`。实际只在最新版 VS Code 上开发和验证。真用到 1.85 没有的 API 时再调高，并在这里写明是哪个 API。

**不作为目标**：Trae、Cursor 等改版编辑器。

### 7. 调 git：起 git 子进程，解析文本输出

**选**：每条命令起一个 git 子进程，解析它的输出。沿用地基期的进程层：禁止 git 停下来等输入，取消时连子进程一起杀。

**否决**：
- isomorphic-git。不跑钩子，不支持 rebase、cherry-pick，签名不完整，大仓库慢。
- nodegit / libgit2。每个平台、每个 Electron 版本要一份原生二进制；读配置、处理钩子的方式和 git 命令行不一致。

**参照**：VS Code 自带的 git 扩展、git4idea、GitLens、旧工程都起 git 子进程。

**代价**：用户机器必须装有 git；每条命令几毫秒的进程开销；输出要自己解析。

### 8. 取数：最多一万条骨架，详情按需取

**选**：
- 先取骨架（每条只有 hash、父提交、时间），最多一万条，超出的直接截断（`--max-count=10000`）。
- 骨架整份发给 webview。webview 按可见行把 hash 交给扩展，取回说明、作者、日期。
- 过滤（第 5 阶段）只在这一万条里做：把骨架的一万个 hash 从 stdin 喂给 `git log --no-walk --stdin`，再加 `--author` / `--grep` / `-- <路径>`。`--no-walk` 让 git 只看喂进去的提交、不顺着父提交走，所以仓库再大也最多检查一万条。git 只返回命中的 hash，webview 按骨架顺序挑出来。
- 分支过滤不走这条路：把骨架命令里的 `HEAD --branches --remotes --tags` 换成那个分支，重新取它自己最近的一万条。骨架命令因此写成可带参数的（起点，以后还有 `--first-parent` 这类遍历选项），不为换起点写特例。

骨架命令：`git log -z --format=<hash、父提交、时间> HEAD --branches --remotes --tags --date-order --max-count=10000`。

**为什么要整份骨架**：滚动条要代表全部行；第 8 阶段的车道布局要每条的父子关系；第 5 阶段跳到某个 hash 要先知道它在第几行。

**为什么一万条**：vscode 仓库（18.8 万条）实测全量骨架 1.9 秒、常驻约 360 MB，按线性外推一万条约 0.1 秒、20 MB。一万条以内不用压缩存储，骨架发给 webview 的序列化开销也小，不必把骨架留在扩展侧再按行号去取。

**否决**：
- 不设上限的全量骨架。几十万条的仓库会让扩展宿主内存溢出，不是慢，是崩。
- 按页取（`--skip`）。滚动条代表不了全部，画图时页与页之间接不上。
- 在全部历史里过滤、结果截到一万条。匹配少时 git 要走完全部历史，16.3 万条的仓库实测 1.2 到 1.3 秒，更大的仓库外推到 10 秒左右；而且过滤后会看到平时列表里没有的老提交，范围前后不一致。
- IDEA 式的压缩存储（整数编号、定长数组）。一万条上限下用不上。

**已知后果**：第一万条那一行的父提交不在列表里，第 8 阶段画图时，那里的线要画成「往下延伸出去」。跳到一个一万条以外的 hash，或者过滤一万条以外的老提交，会找不到。

**实测**（第 5 阶段）：`--no-walk --stdin` 加过滤只看给的提交（有测试）；一万条以上的仓库上几种过滤都在 100 ms 以内、有无匹配一样（`tech/performance.md` 第 3 节）。

### 9. 虚拟滚动：自己写，固定行高

**选**：
- 行高固定，每行一行说明。第 8 阶段的 Graph 列按同一行高画。
- 一个高度为「总行数 × 行高」的占位元素撑出滚动条；按「滚动位置 ÷ 行高」算出首个可见行，只渲染可见行加上下几行余量。
- 可见范围再往前后多取二十来行，一次交给 `getCommitDetails`，取回的存缓存，未取到的行先显示占位。

**否决**：
- TanStack Virtual（有 Vue 版）。它解决的是行高不定、需要实时测量，我们用不上；它的接口本身要学，自己写只有几十行。
- vue-virtual-scroller。适配 Vue 3 的版本长期停在 beta。

**参照**：IDEA 的 `GraphTableModel.getCommitMetadata` 按当前行往上 20 行、往下若干行预取详情，未取到时 `MiniDetailsGetter` 先给占位提交。

**代价**：键盘上下选行、跳到某一行的滚动定位要自己写，在固定行高下都是乘法。

### 10. 历史版本内容：自己的只读文件系统，`git cat-file --filters`

**选**：
- 注册我们自己的 scheme，实现为只读的文件系统。URI 里带提交和路径。
- 读取时执行 `git cat-file --filters <提交>:<路径>`，把原始字节交给 VS Code，由它按用户的编码设置解码。`--filters` 做和检出时一样的转换：换行符（`core.autocrlf`）和 smudge 过滤器（如 Git LFS，否则只读到指针文件）。
- 新增的文件左边给空内容，删除的文件右边给空内容，重命名的文件左边用旧路径。语言高亮由 VS Code 按路径扩展名判断。

**否决**：
- 借用 VS Code 自带 git 扩展的 `git:` scheme。要依赖那个扩展启用、且已识别这个仓库；它的 URI 格式随版本变化。
- 文本内容提供者。它要我们先把字节解码成字符串，非 UTF-8 的文件会乱码。
- 文件系统和文本内容提供者都注册（旧工程的做法）。两个东西回答同一个问题。
- `git show`。不做换行符和 smudge 转换。
- `--textconv`。二进制 diff 现在不做（`product/backlog.md`「暂缓」）。

**diff 模型：多种「边」，左右自由组合**（2026-09-29 补）
- 一个 diff = 左边 + 右边 + 标题。每一边是 `DiffSide` 的一种，左右任意组合，不设限制。
- 四种边：某个提交里的文件（`dummygit:<路径>?rev=<hash>`，只读）；这一边不存在（`?empty`，只读，空内容）；工作区文件（普通 `file:` URI，由 VS Code 提供，可编辑）；暂存区版本（`?stage=<1/2/3>`，只读，冲突用）。
- 三个唯一：唯一的类型 `DiffSide`；唯一的 URI 定义处 `vscode/revisionUri.ts`；唯一的打开函数 `openDiff(左, 右, 标题)`，「只占一个标签」「跟随选中」只在这里实现。
- URI 的路径部分是文件的绝对路径，只是名字，不要求磁盘上存在：删掉、改名、移动过的文件都用那个版本里的路径。
- 各种边在有消费者的阶段才加进 `DiffSide`：前两种第 1 阶段，工作区第 2 阶段，暂存区第 7 阶段。

**参照**：VS Code 自带的 git 扩展（`git` scheme）和 GitLens（`gitlens` scheme）都是只读文件系统。IDEA 用 `git cat-file`，默认带 `--filters`，git 插件只交字节，解码由平台按文件编码做。

### 11. 刷新：文件监听 → 分域 → 事件只说过期

**选**（沿用地基期）：
- 两个文件监听：`.git` 目录一个，工作区一个。
- 事件分到四个域：`refs`（分支、tag、HEAD）、`worktree`（工作区文件）、`stash`、`operation`（停在半路的状态）。被 `.gitignore` 忽略的工作区事件丢弃。
- 防抖 150 毫秒、最多等 1 秒，然后广播哪几个域过期。事件不带新数据，订阅方自己决定拉不拉、拉什么。
- 我们自己的写命令执行完不另发通知，同样靠文件监听。
- 监听哪些目录由第 18 题的「仓库位置」给出，不自己拼 `<根目录>/.git`。现有 `watcher.ts` 写死了 `.git`，在 linked worktree 里监听不到任何东西，要改。

**为什么不带数据**：同一个域过期，不同订阅方要的东西不同（`refs` 变了，Log 要骨架，Commit 面板只要 ahead/behind）；首次加载和刷新走同一段代码，webview 重建后本来就要从头拉。

**否决**：
- 事件带新数据。见上。IDEA 的 `GIT_REPO_CHANGE` 带仓库对象，是因为它的界面和服务同进程，读一下没有成本；我们隔着 `postMessage`，要序列化。
- 写命令完成后主动通知。省下的只是 150 毫秒防抖，外部终端的操作仍要靠监听，两条路回答同一个问题。

### 12. 并发：我们自己的写命令分两条道排队，外部 git 冲突直接报错

**选**：
- 每个仓库**两条道**，各自串行，前一条失败不影响后面排队的独立操作；两条道之间互不等待：
  - **本地道**：改暂存区、工作区、本地引用的命令（commit、merge、checkout、restore…）。
  - **远程道**：网络命令（fetch、`fetch M:B`、push）。它们也写引用（远程分支记录、`fetch M:B` 的本地分支），并发会撞 `cannot lock ref`；放进同一条道后，连点、Fetch 没完就点 Push、自动 Fetch 撞上手动 Pull，都只是排队。
  - 命令的 `LockPolicy` 三态：`None`（读，不进道）/ `Exclusive`（本地道）/ `Remote`（远程道）。
- 读命令不排队。`status` 带 `GIT_OPTIONAL_LOCKS=0`，读时不占锁。
- **一次用户操作 = 一条组合命令**：`execute` 里按顺序调用几次 git，某一步失败即停，后面的步骤不执行，报错原样显示。整条组合只占写队列一个位置，我们自己的其它写命令插不进来。做过的步骤不回滚，所以最容易失败的一步尽量放前面。
- **含网络步骤的组合在网络处拆开**（如拉取当前分支「fetch → `merge --ff-only`」），由上一层按顺序执行，同样上一步失败即停，每一步进各自的道。
- **外部的 git**（终端、别的插件）同时在改这个仓库，超出使用场景：撞锁就把 git 的报错显示给用户，不重试、不抢锁。
- **队列不报告忙闲**。`LockPolicy` 只管正确性（命令能不能同时跑），「正在做」是用户操作层的反馈，见第 15 题旁的「进度出口」。

**否决**：
- 读命令也排队。长时间的写期间界面刷新不了。
- 网络命令占本地写队列。慢推送期间本地什么都做不了。
- 网络命令完全不排队。两个网络命令会撞引用锁，正确性只能靠按钮置灰，而自动 Fetch 这类不经按钮的操作挡不住。
- 撞 `index.lock` 退避重试（VS Code 自带 git 扩展最多重试 10 次）。我们自己的命令已经排队不会互撞，剩下的只有外部 git，那属于使用场景之外，应当告诉用户。

**组合命令清单**（已知的）：第 2 阶段提交带未跟踪文件；第 3 阶段推送新分支（查 upstream → `push -u`）、拉取当前分支（fetch → `merge --ff-only`，拆开）；推送被拒后 rebase 或 merge → 推送（含网络，拆开；需求池）。

### 13. 仓库列表：每个工作区目录取所属仓库，现阶段用第一个

**选**：
- 启动时对每个工作区目录执行 `git rev-parse --show-toplevel`，按 git 返回的根路径去重，按目录顺序合成仓库列表。此后只认这个列表，不再关心工作区目录。
- 现阶段只支持单仓库，用列表第一个。协议里每条消息仍带 `repo`。
- 不扫目录里嵌套的仓库和 submodule。
- 增删目录、调整目录顺序、事后 `git init`，都要重新加载窗口才生效。
- 扩展启动时算出一个「启动结果」，四选一：仓库列表 / 没有打开目录 / 没有仓库 / git 不可用（附原因）。不是仓库列表时，视图直接显示一张只有原因的静态页面，不加载界面脚本；原因同时写进输出面板。`getRepositories` 仍只返回仓库根列表。
- 不弹通知。去掉状态栏入口按钮（面板一直可见，入口不再需要）。

**重名**：同一仓库出现两次（两个目录属于同一仓库）按根路径去重；不同仓库同名（`~/a/app`、`~/b/app`）靠完整路径区分，以后做多仓库界面时再带上上级目录显示。

**否决**：
- 只取第一个工作区目录。它不是仓库而第二个是时，会误报「没有仓库」。
- 跟着当前编辑器所在目录走。切个文件 Log 就可能换仓库。
- 多根时弹选择框。多仓库在需求的池子里。
- 扫嵌套仓库。要遍历文件树、定扫描深度，现阶段只用第一个仓库，扫出来用不上。
- 没有仓库时隐藏面板。插件看起来像没装，用户不知道原因。
- 找不到 git 时弹错误通知。面板一直可见，原因已经在那里。

### 14. 提交：`add` 未跟踪 → `commit --only` → 失败则撤回

**选**：一条组合命令。
1. `git add -- <勾选的未跟踪文件>`。`commit --only` 不认识未跟踪文件，直接给会报 `pathspec did not match`。
2. `git commit --only -- <勾选的全部路径>`。重命名带新旧两个路径；Amend 加 `--amend`。
3. 第 2 步失败（如钩子拒绝），`git reset -q -- <第 1 步加进去的文件>`，暂存区恢复原样，再显示报错。这是第 12 题「做过的步骤不回滚」的例外：第 1 步只为第 2 步服务。

勾选只决定这次提交哪些路径；用户在终端里自己暂存、但没勾选的内容，提交后原样留在暂存区。

**实测**（临时仓库，git 2.43）：`--only` 只提交勾选的修改、删除、新文件，未勾选的已暂存文件原样保留；钩子拒绝后新文件留在暂存区，`reset -q --` 后回到未跟踪。

**否决**：
- IDEA 的四步（存下并移出其它已暂存内容 → 加入要提交的 → 提交 → 恢复）。它是为按行提交和 changelist 服务的，我们都没有。
- 临时 index（`GIT_INDEX_FILE`）。提交后要再同步真实 index，否则提交过的路径显示为「已暂存：改回旧版本」；依赖真实 index 的钩子看到的是另一份。
- 先 `add` 全部勾选文件再普通 `commit`。没勾选但已暂存的内容会被一起提交。

**已知扩展点**：按行提交在需求池子里。`--only` 只能按整个文件提交，做按行提交时，含部分改动的那次提交要改成精确构造暂存内容（IDEA 的做法），这一题要重开。

**已知错误**：写进命令的返回类型，用带 `kind` 的联合类型表达（如推送结果是「成功 / 被拒绝 / 需要密码」），功能代码按 `kind` 分支处理并引导用户。每个已知错误在用到它的阶段、有了消费者时才加。预计会有：

| 阶段 | 已知错误 | 引导 |

| 6 | 提交需要签名密码 | 第 6 阶段改为弹输入框；此前显示 git 原文（2026-09-30 从第 2 阶段推迟：那时签名要密码的处理方式本来就要换） |
| 6 | 没配置用户名或邮箱 | 告诉用户怎么配；此前显示 git 原文（它本身已给出 `git config` 的写法） |

**未知错误**：抛异常，只在三个关口统一处理，功能代码不自己 `catch`：
1. Router：webview 的每个请求（已存在）。
2. 注册 VS Code 命令的包装函数：标题栏按钮、右键菜单。
3. 后台任务：扩展启动、文件变化后的刷新。

关口做同一件事：写日志（2026-10-16 第 12 阶段改，规则见 `CLAUDE.md` G：git 拒绝的命令行、退出码与 stderr 由进程层记，stderr 最多 5 行，关口不再写一遍；已知情况记 warn，我们的 bug 记 error 带调用栈；都带所在操作的编号）；弹 VS Code 错误通知，显示第一行，带「查看输出」按钮；webview 的请求照常回错误响应，让界面停掉进度；同一条错误的通知未关闭前不重复弹（`showErrorMessage` 的 Promise 在关闭时才结束）。

还没实现处理逻辑的已知错误，自然落到未知错误这条路，不需要特殊处理。面板取数失败同样走关口。

**实现时机**：Router 关口第 1 阶段已接入。命令注册包装在第 4 阶段随第一个 `webview/context` 菜单实现：菜单命令用同一张参数校验表把 `data-vscode-context` 校验成协议命令的参数，调同一个 handler，出错交给关口（`tech/decisions.md`「原生右键菜单是协议的第二个入口」）。后台任务关口在第一个会往外抛错的后台任务出现时实现。

**进度出口**（与错误关口对称，第 3 阶段起）：`vscode/` 层一个统一出口，注入给 handler（同确认框、打开 diff）。
handler 声明「这一段是什么」（`Pushing zzc-dev`）与「做完了怎么说」（`Pushed zzc-dev → origin/zzc-dev`），
出口负责显示：进行中在状态栏转圈加文字，结束后几秒的完成消息；失败交给错误关口。它只显示、不保存状态。
哪些操作要用由 handler 定：用户点了、要等、界面上不一定马上看得出结果的（网络操作、checkout、stash…）；提交不用（按钮自带 `Committing…`）。
以后面板也要知道「谁在跑」时，在 `Repository` 加「进行中的操作」与对应的域，出口改由它驱动，handler 写法不变。
否决：按 `LockPolicy` 自动显示进度——一个用户操作可能横跨两条道或包含组合命令，读命令后台自动跑不该显示，等确认框的时间也不该算在内。

**否决**：
- 每个功能自己 `catch`、自己弹通知。会漏，文案不统一。
- 已知错误也抛异常、在关口按错误码分流。关口要认识每个功能的引导流程，功能逻辑散到关口里。
- 面板取数失败只在面板里显示、不通知。统一走关口，去重防刷屏。

**参照**：VS Code 自带的 git 扩展和 IDEA 都是弹通知，完整输出放在输出面板或 Git 控制台。

### 16. 要密码时直接报错：askpass 给空回答，GPG 交给系统

**选**（第 2 到第 5 阶段）：
- `GIT_ASKPASS`、`SSH_ASKPASS` 都指向我们自己的一个脚本，内容只有 `echo ''`：git 或 ssh 一要密码就拿到空字符串，认证失败退出。覆盖 HTTPS 账号密码、SSH 私钥口令、首次连接确认主机指纹、SSH 签名口令。
- `SSH_ASKPASS_REQUIRE=force`，让 ssh 只走 askpass、不走终端。
- 保留 `GIT_TERMINAL_PROMPT=0`。进程层 `detached: true` 让 git 脱离终端，ssh 拿不到 tty。
- GPG 签名不拦，交给系统 pinentry：桌面上弹系统窗口，没有图形界面时通常直接失败。
- Git Credential Manager 不拦：它弹的是看得见的窗口。凭据助手里已存的密码照常用。
- 失败时的 stderr 实测后写进第 15 题的已知错误「需要密码」。

第 6 阶段把 `echo ''` 脚本换成回调扩展、弹输入框的版本，结构不变。

**否决**：
- ssh 加 `-o BatchMode=yes`。要改 ssh 命令，还得避免覆盖用户的 `core.sshCommand`；`SSH_ASKPASS_REQUIRE=force` 已经够。
- `GCM_INTERACTIVE=never`。两家都不拦，它不会悄悄卡住。
- 用 `gpg.program` 包一层、加 `--pinentry-mode=error` 强制 GPG 失败。两家都不这么做。
- 给网络命令加超时。先卡用户几十秒，再给一个说不清原因的失败。
- 没有 `DISPLAY` 时补 `:0.0`（IDEA 为 OpenSSH 8.4 以下做的兼容，旧版不认 `SSH_ASKPASS_REQUIRE`）。8.4 是 2020 年的版本，只在 RHEL 8 这类老服务器上还常见，不是目标环境；假 `DISPLAY` 还会让 GPG 的 pinentry 去连不存在的显示器。不补的后果只是旧版 ssh 要口令时直接失败。

**参照**：VS Code 自带的 git 扩展用 `GIT_ASKPASS` + `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`，回调通道不可用时换成只 `echo ''` 的脚本；GPG 和 GCM 不管。IDEA 同样用这两个变量加 `force`，另补 `DISPLAY` 并脱离 tty；GPG 的内嵌 pinentry 默认关闭。

### 17. 输入密码：askpass 回调扩展弹输入框，GPG 不接管

**选**：
- 把第 16 题的 `echo ''` 脚本换成回调版：git 或 ssh 调用脚本 → 脚本以 `ELECTRON_RUN_AS_NODE=1` 用编辑器自带的 Node 跑我们的一小段 JS → JS 经本地 socket 连回扩展 → 扩展弹 VS Code 输入框（密码用密码模式，主机指纹用「是 / 否」选择框）→ 答案原路返回。
- 覆盖 HTTPS 账号密码、SSH 私钥口令、SSH 签名口令、主机指纹确认。
- 插件不存密码。认证成功后 git 自己交给用户配置的凭据助手保存。
- 用户取消输入框，回空字符串，操作按失败处理。
- GPG 签名始终交给系统 pinentry。

**否决**：
- IDEA 的内嵌 pinentry：改写用户的 `~/.gnupg/gpg-agent.conf`。改的是全局配置，终端里签名也会走我们的脚本，VS Code 关着就签不了；IDEA 自己默认关闭。
- `gpg.program` 包装加 `--pinentry-mode loopback`。两家都没有，agent 已缓存口令时的行为未验证。

**参照**：VS Code 自带 git 扩展的 `askpass.sh` / `ssh-askpass.sh` 经 IPC 回调扩展弹输入框，GPG 不管；IDEA 的 `GIT_ASKPASS` / `SSH_ASKPASS` 回调 IDE 对话框。

### 18. 进行中的操作：读状态文件；仓库的所有路径只从一处来

**仓库位置：统一来源**
- 打开仓库时（第 13 题），一次 `git rev-parse` 同时问出：仓库根（`--show-toplevel`）、本工作树的 git 目录（`--git-dir`）、共享 git 目录（`--git-common-dir`），以及要用到的每个状态文件的实际位置（多个 `--git-path <名字>`）。相对路径按执行目录解析成绝对路径。
- 结果存成一个不可变的「仓库位置」对象，由 `Repository` 持有。文件监听、状态读取、任何要碰 git 目录的代码都从它取路径，不许自己拼 `.git/…`。
- 实测（linked worktree）：`MERGE_HEAD`、`rebase-merge`、`index` 在本工作树专属目录 `…/.git/worktrees/<名字>` 下，`refs/heads` 在共享目录下；从子目录执行结果相同。

**进行中的操作**
- 读状态文件，按顺序判断，结果五选一（带 `kind`）：无 / rebase（`rebase-merge/` 或 `rebase-apply/`）/ merge（`MERGE_HEAD`）/ cherry-pick（`CHERRY_PICK_HEAD`）/ revert（`REVERT_HEAD`）。
- 收到 `operation` 域过期事件时重读。
- 哪些文件有冲突不在这里判断，从 `git status` 的未合并条目取。

**否决**：
- 解析 `git status` 长格式里「You are currently rebasing」之类的话。给人看的文字，随版本和语言变。
- 写死 `<根目录>/.git/…`（VS Code 自带 git 扩展的做法，`repository.ts:3126-3151`）。linked worktree 和 submodule 里 `.git` 是文件，读不到。
- 每次要用某个路径时临时问 `git rev-parse --git-path`。多起进程，而且同一个问题有了多处答案。

**参照**：IDEA 的 `GitRepositoryFiles` 按工作树目录集中管理这些路径；VS Code 写死 `.git/`。

### 19. 冲突：自己调 `_open.mergeEditor`，标记已解决只有一条路

**选**：
- 双击冲突文件，调用 VS Code 内部命令 `_open.mergeEditor` 打开合并编辑器。三方内容由第 10 题的只读文件系统提供：`:1:<路径>` 基准，`:2:<路径>` 我们这边，`:3:<路径>` 对方；输出是工作区里这个文件。
- 标记已解决只走我们自己的一条路：冲突组里「标记已解决」，执行前检查冲突标记（第 7 阶段需求）。合并编辑器里没有 Complete Merge 按钮，用户保存后回来标记。
- `_open.mergeEditor` 调用失败按未知错误走关口（第 15 题），不退回普通编辑器。
- 冲突组的内容来自 `git status` 的未合并条目，不依赖是否有进行中的操作（第 18 题）。stash 取出时冲突没有进行中的操作，照样显示冲突组。

**以后**：需求池子里有自建三方合并编辑器，尤其用于 autostash 冲突。到时替换的只是「双击打开什么」，三方内容的来源（`:1` / `:2` / `:3`）和「标记已解决」不变。

**否决**：
- 借用自带 git 扩展的 `git.openMergeEditor`。依赖另一个扩展，Complete Merge 后会跳到源代码管理视图，而且它和我们的「标记已解决」是两条路回答同一个问题。
- 调用失败时退回普通编辑器。两种打开方式并存，行为不确定。

**参照**：GitLens 不用 `git.openMergeEditor`，直接调 `_open.mergeEditor` 并自己提供四个 URI；冲突文件的处理是「看某一边改动」「整个文件取某一边」加暂存前检查冲突标记。

### 20. 图：每行一段 SVG，布局在 webview 用纯函数算

**选**（2026-10-14 按 IDEA 的做法细化，交互见 `product/features/graph.md`）：
- 虚拟列表每一行自带一小段 SVG，只画本行的节点、上下连线和折角。图画在 Message 单元格最左边，没有单独的列；每行文字按本行图的宽度退让。行高与第 9 题一致，颜色用主题 CSS 变量。
- 布局是 webview 里的纯函数模块，不碰 DOM，可在 node 里单测。输入：整份骨架 + refs（排车道用）+ 可选的「筛选后的 hash 列表」；输出：每个可见行的元素（本行节点与穿过的线各在第几个位置）与本行宽度。
- 车道：整张图按头的顺序沿第一父提交编一次号，每行按编号排序得位置，车道始终压紧。跨度 ≥ 30 行的线只画两头带箭头。
- 不筛选时所有行可见。按作者、说明文字、路径、日期筛选时只留匹配的行，中间隔着被跳过提交的连接画成虚线（线性时间，只连最近的可见祖先）。按分支筛选是换一份骨架。
- 骨架、refs 或筛选变了就整个重算，不做增量。一万条预计毫秒级，第 8 阶段实测后记进 tech/performance.md。
- 截断处（第一万条）的父提交不在列表里，那几条线画到行底并渐隐。
- GitLens 把穿过的竖线预先合成小图的优化先不做，实测卡顿再加。

**否决**：
- Canvas。高分屏缩放、主题颜色、点击命中都要自己处理；四家参照都没用。
- 一整张大 SVG（vscode-git-graph）。一万行元素太多，与虚拟滚动不兼容。
- 在扩展侧算布局。骨架在 webview，算完还要传回去。

**参照**：IDEA 按行绘制，整历史拓扑只建一次，筛选时派生「可见图」隐藏不匹配的提交、用虚线（`DottedFilterEdgesGenerator`）连接；GitLens 每行一段 SVG，布局在独立的纯逻辑包；旧工程 SVG 只画可见行。

### 21. 改写历史：只改说明的在内存里造提交，其余 `rebase -i --autostash`

**选**：
- reword（第 11 阶段，2026-10-15 改）在内存里造提交：说明变、内容（tree）不变，从被改的那条到 HEAD 逐条 `commit-tree <原 tree> -p <新父提交>`，再 `update-ref HEAD <新> <旧>` 移动分支（带旧值：读完之后 HEAD 被动过就失败）。不可能冲突，不碰工作区。要求那条到 HEAD 是一条直线、没有合并提交。以后连续一段的 squash 同理（合出来的内容就是最新那条的 tree）。
- squash（不连续时）、fixup、drop、交互式 rebase 走 `git rebase -i --autostash`。`GIT_SEQUENCE_EDITOR` 指向我们的脚本，写入准备好的 todo 列表；`GIT_EDITOR` 指向脚本，写入新的提交说明。
- `--autostash`：工作区有未提交改动时 git 先存起来、结束后取回。取回冲突时没有进行中的操作，但有未合并文件，照样显示冲突组（第 19 题）。
- 中途冲突停下，用第 7 阶段的冲突组（标题行的继续与放弃），不另写一套。
- reset、撤销最近一次提交、弹出最上面几条，都是一条 `git reset`，不经 rebase。

**以后**：需求池子里有「改写历史时完全不碰工作区」。到时加 IDEA 那样的内存版（`commit-tree` 等底层命令造提交再移动分支），冲突时退回本题的做法。

**否决**：
- reword 走 `rebase -i` 加两个脚本（原定，2026-10-15 改掉）：内容不变的改写用不上检出、autostash、停下与继续，却要为它写脚本、管 Windows。
- 内存版为主、`rebase -i` 兜底（IDEA 的 `executeInMemoryWithFallback`）。会冲突的改写才走 `rebase -i`，不对同一种操作准备两套。
- 只用内存版。遇到冲突做不下去。
- 不加 `--autostash`、要求工作区干净。改一条老提交的说明也得先手动 stash。

**参照**：IDEA 先调内存版（`inMemory/rebase/`），不完成再走普通 rebase，普通 rebase 用 `GIT_EDITOR` 指向 IDE 的脚本；GitLens 只用 `rebase -i`，给 todo 文件做了图形化编辑器。

### 22. 测试：只测一跑看不出来的

| 层 | 测什么 | 怎么测 | 进 `pnpm check` |
|---|---|---|---|
| 纯逻辑 | 扩展侧现有部分；webview 的 `logic/`（车道布局、虚拟滚动行号、树的勾选联动、协议客户端） | Vitest，纯 node | 是 |
| 验收 | 每一步、每阶段的验收句 | 手动走一遍 | — |

原则：一打开插件就能看出来的问题（激活失败、视图没注册、界面空白）不写测试，用户每天用最新版插件，第一次打开就会暴露。测试只留给看不出来的：时序、边界输入、回归时悄悄变错的数据。沿用 `process/testing.md` 的判据：断言失败时是不是真的坏了。webview 里有逻辑的都抽进 `logic/`，Vue 组件只摆数据，不单独写测试。

**否决**：
- 宿主冒烟测试（`@vscode/test-cli` 下载真 VS Code 跑）。它测的都是一跑就能看出来的事，却要虚拟显示器、每次下载 VS Code、几十秒一轮，远程环境下还容易时好时坏。
- Vue 组件单元测试（`@vue/test-utils` + 模拟 DOM）。组件是胶水，断言失败多半只是界面改了。
- 端到端界面自动化（如 Playwright 点 webview）。搭建贵，时好时坏。
